# 🔥 Phoenix RAG Bot — העוזר הדיגיטלי של הפניקס

בוט שאלות-ותשובות בעברית על מוצרי ושירותי **חברת הפניקס**. המערכת מחפשת
במאגר תוכן שנסרק מהאתר הרשמי [fnx.co.il](https://www.fnx.co.il), מדרגת את
התוצאות, ומציגה קישורים למקורות שנשלפו. תשובות תלויות באיכות האינדקס והחיפוש;
כאשר אין התאמה מספקת, או כאשר בדיקת הרלוונטיות נכשלת, הבוט נמנע מתשובה
מבוססת-מקורות ומבקש לנסות שוב או לפנות לשירות.

הבוט בנוי בשיטת **RAG** (Retrieval-Augmented Generation): הוא משלב חיפוש וקטורי
עם BM25, ממזג ומדרג את המועמדים, ומעביר את הקטעים שעברו את סף הרלוונטיות ל-Gemini
לניסוח תשובה. כתובות המקורות מוצגות באזור נפרד מהתשובה.

---

## 🎯 מה הבוט עושה

1. **סורק** את אתר הפניקס, מנקה את ה-HTML ומחלק את התוכן לקטעים (chunks) חופפים.
2. **מטמיע** (embedding) כל קטע לווקטור באמצעות Gemini ושומר ב-ChromaDB.
3. בזמן שיחה — **מחפש ומדרג** קטעים באמצעות חיפוש היברידי (וקטורי + BM25 + RRF)
   וקריאת reranking אחת ל-Gemini, ואז **מזרים** תשובה בעברית ומציג מקורות בנפרד.
4. משתמש במטמון תוצאות חיפוש קצר-חיים לשאלות זהות לאחר נרמול; המטמון מוגבל
   בזמן ובגודל ומקומי לתהליך שרת יחיד.
5. תומך בשתי פרסונות: **מצב לקוח** (ידידותי, ברור ומקצועי) ו**מצב סוכן**
   (מקצועי ומפורט), עם שאלות פתיחה והצעות המשך המבוססות על נושא המקורות.
6. בוחר באקראי תמונת נציג לכל שיחה ומשתמש בה בעקביות עד לפתיחת שיחה חדשה.

## 📜 הכללים שהבוט מחויב להם

הנחיות הטון והגבולות מוזנות כ**הגדרות** (קובצי YAML תחת `config/`); סף
הרלוונטיות, מדיניות הכשל והגנות הממשק ממומשים בקוד:

| כלל | מימוש |
|------|--------|
| **מקור יחיד** | התשובות מבוססות אך ורק על התוכן שנשלף מאתר הפניקס. |
| **מקורות** | הממשק מציג באזור נפרד קישורים לעמודים שנשלפו; נוכחות מקור אינה כשלעצמה ציון ביטחון או הוכחה שכל טענה בתשובה נתמכת. |
| **הימנעות** | תוצאות שעברו ניקוד נמוך אינן משמשות לתשובה. אם בדיקת הרלוונטיות נכשלת טכנית, הבוט מציג שגיאה זמנית במקום להחזיר מועמדים לא מאומתים. |
| **גבולות** | הפרסונות מונחות לא לספק ייעוץ אישי או מידע על תיק, חשבון או פוליסה של אדם מסוים. |
| **עברית** | תשובות בעברית ברורה וקצרה, עם הזמנה לשאלת המשך. |

## 🏗️ ארכיטקטורה

שני צינורות נפרדים:

**Offline — בניית מאגר הידע:**
```
אתר הפניקס  →  Crawler  →  ניקוי HTML + Chunking  →  Embedding (Gemini)  →  ChromaDB
```

**Online — מענה לשאלות:**
```
משתמש → React UI → FastAPI → חיפוש היברידי (וקטורי + BM25 + RRF + Rerank)
                                     → בדיקת רלוונטיות (Gemini, קריאה אחת)
                                     → ניסוח תשובה זורמת + מקורות בממשק
```

### האם השתמשנו במיקרוסרוויסים?
לא, ובכוונה. המערכת היא **מונוליט מודולרי** — שירות FastAPI אחד עם מודולים
מופרדים (crawler, indexer, retriever, generator, session, llm, api). פשוט יותר
לפריסה, מהיר יותר (קריאות בזיכרון), ומתאים לגודל הפרויקט — ועדיין קל לחלץ מודול
לשירות עצמאי בעתיד אם יידרש.

## 🔁 רוצים לשכפל לחברה אחרת?

הפרויקט בנוי להתאמה לארגונים נוספים באמצעות הגדרות tenant והנחיות פרסונה.
התאמות בסיסיות כוללות:

| מה לשנות | איפה |
|-----------|------|
| שם החברה, URL לסריקה, עומק הסריקה | `config/phoenix.yaml` |
| אופי הבוט ללקוח — טון, גבולות, הגבלות | `config/personas/customer.yaml` |
| אופי הבוט לסוכן — שפה מקצועית, ציטוטים | `config/personas/agent.yaml` |

מחליפים את ההגדרות, מתאימים את מדיניות המקורות ומריצים את ה-Crawler. יש לבדוק
ולאמת את התוכן וההתנהגות עבור כל ארגון חדש; החלפת קובצי YAML לבדה אינה מבטיחה
כיסוי מלא או תשובות מדויקות.

## 🔁 עדכון מאגר הידע

התצורה כוללת לוח סריקה שבועי לדוגמה, אך הסורק המתוזמן **כבוי כברירת מחדל**.
הוא מופעל רק אם מגדירים `PHOENIX_ENABLE_SCHEDULER=1`; תזמון בענן תלוי בכך
שהתהליך נשאר פעיל ואינו מובטח בסביבת Serverless. הסריקה אינה בזמן אמת.

הרצה ידנית:
```bash
python -m backend.crawler.cli --tenant config/phoenix.yaml          # אינדוקס טרי
python -m backend.crawler.cli --tenant config/phoenix.yaml --sync   # ריסריקה + סנכרון
```

## 🚀 הרצה מקומית

```bash
# 1. התקנת תלויות לשרת, לסריקה ולבדיקות
pip install -r requirements-dev.txt

# 2. מפתחות — להעתיק .env.example ל-.env ולמלא GEMINI_API_KEY
copy .env.example .env

# 3. בניית מאגר הידע (פעם אחת)
python -m backend.crawler.cli --tenant config/phoenix.yaml

# 4. הרצת הבקאנד
python -m backend.main               # http://localhost:8000

# 5. הרצת הפרונטאנד
cd frontend && npm install && npm run dev   # http://localhost:5173
```

## 🛡️ עמידות: מנגנון fallback

הלקוח `backend/llm/gemini_client.py` מספק:
- **Fallback בין מודלים** — על 503/timeout עוברים למודל הבא ברשימה.
- **Fallback בין מפתחות** — על 429 (מכסה) מתגלגלים למפתח הבא (עד 5 מפתחות).
- **טיימאאוט קשיח** + REST transport (תאימות לרשתות עם בדיקת SSL כמו NetFree).

- **קישור למשתמשים (Frontend):** [https://projects-production-77a3.up.railway.app](https://projects-production-77a3.up.railway.app)

- **Backend (בדיקת מוכנות לבוט):** [https://projects-production-5e07.up.railway.app/api/ready](https://projects-production-5e07.up.railway.app/api/ready)

ה-Frontend שולח בקשות API ל-Backend שלמעלה; אפשר להגדיר בשירות ה-Frontend את
`VITE_API_BASE_URL` לכתובת ה-Backend. לפרטי הגדרה ובדיקות מוכנות ראו
[DEPLOY.md](./DEPLOY.md). למדריך דמו, ארכיטקטורה ותשובות לשאלות שופטים ראו
[PRESENTATION_GUIDE.md](./PRESENTATION_GUIDE.md).

## 🧪 מצב בדיקות ומגבלות ידועות

- בדיקות היחידה וה-build נועדו לתפוס נסיגות בקוד; הן אינן מוכיחות שכל שאלה
  אפשרית תקבל מקורות נכונים.
- איכות התשובה תלויה בסריקה, באינדקס ובדירוג הרלוונטיות. יש לבדוק שאלות
  מייצגות, כולל שאלות שאין עליהן מידע ושאלות פרטיות.
- לא מוצג ציון ביטחון מכויל. חיווי המקורות במצב סוכן מתאר את המקורות שהוחזרו,
  ולא הסתברות לנכונות.
- אם דירוג המקורות נכשל, המערכת נכשלת באופן סגור ואינה מציגה תוצאות חיפוש
  גולמיות כאילו אומתו.
